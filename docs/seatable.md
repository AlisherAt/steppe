# SeaTable + Vercel

Провайдер SeaTable реализован. Для базы `Steppe` на `https://cloud.seatable.io` проверены настоящие запросы авторизации, создания таблиц, чтения, записи, изменения и удаления временной служебной записи. Реальные товары не добавлялись: разрешённые фиды магазинов ещё не подключены.

## Настройки Vercel

Проект → Settings → Environment Variables → Production:

```dotenv
DATABASE_PROVIDER=seatable
SEATABLE_SERVER_URL=https://cloud.seatable.io
SEATABLE_BASE_NAME=Steppe
SEATABLE_WORKSPACE_ID=114607
SEATABLE_API_TOKEN=ваш_API_токен_с_правами_чтения_и_записи
CRON_SECRET=случайная_строка_минимум_32_символа
RATE_PROVIDER=nbk
```

`SEATABLE_API_TOKEN` и `CRON_SECRET` задаются как Secret, остальные значения могут быть Config. Не добавляйте `NEXT_PUBLIC_`. В окружении локального проекта используются те же значения в `.env.local`; он исключён из Git. Без явно заданного `DATABASE_PROVIDER` наличие SeaTable-токена автоматически выбирает SeaTable. `SEATABLE_BASE_NAME` и `SEATABLE_WORKSPACE_ID` защищают от случайного подключения другой базы.

Для генерации CRON_SECRET локально:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Сохраните сгенерированное значение в Vercel и GitHub Actions Secrets. API-токен базы и секрет планировщика должны быть разными. Токен базы нужен только серверу Vercel; GitHub-задаче он не нужен.

После сохранения настроек выполните **Redeploy** версии с поддержкой SeaTable. Если Git-интеграция Vercel включена, push в main запустит новый deploy, но его успех нужно проверить в Deployments.

Проверка: `/api/health` должен вернуть `{"status":"ok","database":"seatable",...}`. Ответ 503 означает проблему настройки/структуры/доступа. Endpoint не выдаёт ключи, идентификатор базы и содержимое таблиц. Результат проверки кешируется до 60 секунд.

## Создание таблиц

В вашей базе эти таблицы уже созданы. Повторная настройка или новая база:

```sh
npm run seatable:setup
npm run seatable:check
npm run seatable:check -- --verify-write
```

Setup создаёт только отсутствующие служебные таблицы и записи источников. Чужие таблицы, включая `Table1`, не удаляет; существующую паузу магазина сохраняет. Если оператор переименовал служебный столбец/изменил тип, проверка выдаст `SEATABLE_SCHEMA_MISMATCH`, вместо молчаливой потери данных.

- **STEPPE_Sources** — `id`, название и флаг `paused`. Для остановки магазина включите checkbox `paused` в SeaTable.
- **STEPPE_Offers** — версии предложений: `source_id`, `product_id`, `snapshot`, исходный и пересчитанный товар в JSON `payload`. Технические строки не редактируйте вручную: проверяется контрольная сумма снимка.
- **STEPPE_Runs** — журнал запусков, `running` / `success` / `error`, число товаров, даты, контрольная сумма и использованные курсы `rates`. Курсы и исходная валюта также сохраняются в каждой карточке.

В таблицах нет демотоваров. Начальные 11 записей Sources — только конфигурация магазинов, они не означают, что магазин подключён.

## Автоматическое расписание без Supabase

Основное расписание — [Планировщик Windows](local-scheduler.md), ежедневно в 10:00 и 21:00 по времени компьютера. Он собирает товары локально, отправляет отчёт и запускает импорт в SeaTable через Vercel.

`.github/workflows/refresh.yml` сохранён для **ручной диагностики**, без автоматического cron:

1. GitHub → репозиторий **AlisherAt/steppe** → **Settings → Secrets and variables → Actions → New repository secret**.
2. Имя **CRON_SECRET**, значение **точно такое же**, как в Vercel.
3. В Actions откройте **«Обновить каталог STEPPE» → Run workflow** для первого запуска. Если Actions отключены в репозитории, включите их.
4. По умолчанию запрос отправляется на `https://steppe-gray.vercel.app/api/cron/refresh`. Для другого домена задайте Repository Variable `STEPPE_SITE_URL`.

GitHub workflow запускается только вручную. Не запускайте его одновременно с локальной задачей: это создаёт конкурирующие снимки и дополнительные запросы. Если ранее включался Supabase Cron, отключите его. Статус `needs_configuration` означает отсутствие подключённого фида.

Не отключайте авторизацию `/api/cron/refresh`. При Vercel Deployment Protection требуется разрешить доступ планировщику к production URL предусмотренным Vercel способом. Включите Fluid Compute: серверная задача ограничена 300 секундами. После 220 секунд новые импорты не начинаются; долго не проверенные магазины получают приоритет следующего запуска. При систематическом исчерпании бюджета нужно разделить задачи.

**Для локального расписания секрет хранится в `.env.scheduler.local` и должен совпадать с Vercel. Проверяйте результат в `artifacts/local-refresh/latest.json`.**

## Согласованность и ограничения

SeaTable не заменяет PostgreSQL-транзакции и SQL RPC. Для него используется другой протокол: сначала записывается неизменяемый снимок предложений, проверяются число строк, схема, отсутствие повторов и SHA-256, затем единственная строка запуска получает статус `success`. Читатель выбирает последний по времени начала успешный снимок магазина. Позднее завершение старого запуска не вытесняет более новый. Оборванная загрузка не становится каталогом; предыдущая успешная версия остаётся до истечения 36 часов. Успешный пустой снимок скрывает все прежние товары.

Снимки и история не растут бесконечно: перед обновлением удаляются ненужные версии после двухчасового периода с момента публикации замены; журнал старше 7 дней очищается, кроме последнего успешного запуска каждого магазина. Незавершённые запуски после шести минут показываются как прерванные. В SeaTable нет распределённой блокировки данного приложения; параллельные записи безопасны благодаря независимым снимкам, но расходуют дополнительную квоту API. Регистрацию новых магазинов выполняйте одним setup/cron за раз; повторяющиеся ID источника считаются ошибкой.

Чтение каталога/статусов кешируется сервером с ревалидацией раз в 60 секунд, включая изменения `paused`; корзина перед переходом перечитывает актуальные данные напрямую. При отказе ревалидации Next.js может временно сохранить предыдущий кеш; фильтр времени всё равно скрывает просроченные предложения. Проверка здоровья тоже кешируется. Публичных ссылок на базу и токенов в браузере нет.

Пагинация SeaTable читается полностью по 1000 строк. Максимум чтения одной таблицы — 100 000 строк; превышение вызывает ошибку, не усечение. Один импорт — до 1000 предложений магазина. Запись разбита на пакеты по 100. Число строк, версия снимков и API-запросы должны укладываться в **тариф вашей SeaTable**; его ограничения могут быть ниже лимитов приложения. Для большого каталога/Postgres-поиска сохранён вариант `DATABASE_PROVIDER=supabase`. SeaTable в этой версии выполняет поиск по загруженному снимку в памяти сервера.
